# 设计说明

本文记录实现中的技术决策、被放弃的方案和已知代价。目标不是证明当前方案最优，而是让
后来者能判断：在什么规模、什么约束下它成立，什么时候应该换。

## 1. 目标与非目标

### 目标

- 给物流售后/客服一个可查询内部政策的问答接口；
- 回答必须能追溯到文件名和章节，依据不足时必须拒答；
- 默认离线、确定性，测试与 demo 不依赖外部模型；
- 在单机、零外部服务的前提下，把入库、检索、生成、评测完整跑通；
- 保留切换真实 embedding / rerank / LLM 的清晰接口。

### 非目标

- 不做通用对话助手，不做工单系统对接；
- 不解决企业级权限、多租户与审计合规；
- 不在当前阶段建设分布式向量库；
- 不追求在公开 benchmark 上刷分。评测集是自建的，只用于回归。

## 2. 数据流

### 入库

```text
文件扫描
  → SHA-256 判断是否变更
  → 按扩展名解析为文本 + 元信息
  → Markdown 标题扫描，生成 heading_path
  → 章节内按段落打包 / 超长段落滑窗
  → 分块文本（含标题）向量化
  → 单事务写入 documents + chunks
```

单个文件的失败被隔离：记录到 `IngestReport.errors` 或 `.warnings`，继续处理下一个文件。
缺少 python-docx/openpyxl/pypdf 时，该格式记为跳过并给出安装提示，不让整批任务失败。

### 查询

```text
问题
  → 查询向量（与入库同一 Embedder）
  → 向量余弦 topN
  → BM25 topN
  → RRF 融合
  → 可选重排
  → 生成（mock 抽取 / HTTP chat）
  → 回答 + Citation
```

线上查询与离线评测走完全相同的 `RAGService.answer`，避免出现「评测脚本一套逻辑、
接口另一套逻辑」。

## 3. 分块：标题层级是第一位

### 问题

物流政策是强层级文档：

```text
# 货物破损理赔流程
## 所需材料
## 定损与赔付
### 保价货物
### 未保价货物
```

定长 500 字切分会产生两个问题：

1. 引用只能给文件名，客服无法快速定位；
2. 一个分块同时包含「保价」和「未保价」两段，生成时容易把赔付规则串在一起。

### 实现

`MarkdownChunker` 逐行扫描，维护 `headings[level]` 栈：

- 遇到 `#` 到 `######` 时更新栈，丢弃比当前更深的层级；
- 输出 `heading_path`，如 `("售后与退货政策", "退货时效", "退款到账时效")`；
- 代码围栏内的 `#` 不当作标题；
- 每个章节内先按空行拆段落，段落总长不超过窗口时合并；
- 单段超过窗口时按 `。！？!；` 等句末标点切句，再按 `chunk_size / overlap` 滑窗；
- 单句仍超长时退化为带重叠的硬切分，保证不超过窗口。

默认窗口 650 字、重叠 120 字。物流政策单节通常在 100–400 字，650 能保留完整上下文；
重叠用于长条款，避免一句话被切成两半。`ordinal` 在文档内从 1 递增，便于稳定排序和
展示。

### 代价

- 强依赖 Markdown 标题；纯 TXT 或扫描 PDF 没有标题时，所有内容归入无标题章节，引用
  只能到文件级。
- 表格被转成行文本后，跨行表头含义会丢失。
- 章节内部仍可能合并多个主题，只是比定长切分好。

## 4. Embedding

### HashEmbedder（默认）

- 中文取连续汉字的字符 bigram；单字成词时保留单字；
- 英文/数字按词，保留 `-`、`_`、`.` 等连接符；
- 特征串加固定 salt 后做 BLAKE2b，取前 4 字节映射到 512 维，取一位决定符号；
- 词频使用 `1 + log(tf)` 抑制长文本重复词；
- 向量做 L2 归一化。

为什么用 BLAKE2b 而不是 Python `hash()`：后者受 `PYTHONHASHSEED` 随机化影响，进程重启
后同一文本会得到不同向量，数据库中的旧向量立即失效。salt 固定在配置里，保证跨进程、
跨机器可复现。

为什么保留符号：纯非负哈希容易让无关词在余弦空间中同向累积；随机符号能降低碰撞偏差，
代价是可解释性更弱。

它不理解「退款」和「返还货款」是近义，也不理解中英文同义。它只用于离线回归、demo 和
测试，不被当成生产语义模型。

### HttpEmbedder

- OpenAI 兼容 `/embeddings`，支持 base 以 `/v1` 结尾或直接给完整端点；
- 批量请求，默认 16 条一批；
- 超时、429/5xx/连接错误指数退避重试，最多 `LLM_MAX_RETRIES` 次；
- 响应按 `index` 重排，校验条数与维度；
- 返回向量同样归一化，保证余弦计算一致；
- API Key 只存在内存和请求头，不写日志、不写 DB。

维度在第一次响应后确定；切换模型后旧库维度不匹配，`vector_search` 会抛出明确错误，
提示重新入库，而不是默默算出错误结果。

## 5. BM25

### 分词

- 连续汉字切成字符 bigram，例如「退款到账」→ `退款 / 款到 / 到账`；
- 英文和数字按词，统一小写；
- 标点不进入索引；
- 不使用 jieba，避免核心路径引入词典和第三方依赖。

中文 bigram 的召回粒度比词更细，容易出现「款到」这种无意义词项，但 BM25 的 IDF 会
自动压低高频噪声；在内部知识库这种术语重复度高的语料里，效果足够作为向量互补通道。

### 打分

标准 BM25：

```text
idf(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))
score(D, Q) = Σ idf(t) · tf · (k1 + 1)
              / (tf + k1 · (1 - b + b · |D| / avgdl))
```

默认 `k1=1.5, b=0.75`，可通过 `BM25_K1` / `BM25_B` 覆盖。标题在索引文本中出现两次，
让章节词略占优势；这是简单的字段加权替代方案。

### 规模上限

当前实现每次查询重建内存 BM25 索引，语料 49 个分块时耗时在毫秒级。万级以上应改为
持久化倒排表或 SQLite FTS5，并缓存索引版本。

## 6. 混合检索与 RRF

### 为什么需要两路

- 向量通道：处理「到账要多久」和「退款多久能收到」这类字面不同但语义接近的问法；
- BM25 通道：处理精确金额、百分比、天数、专有名词，向量对数字不敏感。

只有向量时，`6000` 和 `3000` 在哈希空间可能很近；只有 BM25 时，问法和原文措辞不一致
就会漏召回。

### RRF

```text
rrf(d) = Σ 1 / (60 + rank_channel(d))
```

只使用排名，不使用原始分数。原因是余弦相似度与 BM25 分数的量纲、分布、随语料变化的
方式都不同；加权和需要为每个语料调权重。RRF 的代价是丢失分数的绝对信息：一个通道
第 1 名和第 2 名对融合贡献差距很小，所以它更适合「先保召回，再重排」。

每条 `SearchHit` 保留：

```text
vector_rank / vector_score
bm25_rank / bm25_score
rrf_score / rrf_norm
rerank_score
content_term_coverage / heading_hit / title_hit / length_fit
```

这些字段不是调试彩蛋，而是客服排障和后续调参的依据。

### 重排

启发式公式：

```text
rerank = 0.50 · 章节内词覆盖率
       + 0.25 · 章节标题命中率
       + 0.15 · 文档标题命中率
       + 0.10 · 长度合适度
```

- 章节标题去掉文档 H1 后再计算，否则所有分块都会蹭到文档标题；
- 标题命中率按标题词数归一，避免长标题天然获得高覆盖；
- 长度合适度以 350 字为中心，过短上下文不足，过长稀释重点；
- 最终分 = `0.45 · 归一化 RRF + 0.55 · rerank`。

为什么保留 RRF 权重：重排是启发式规则，可能把 BM25 的精确命中压掉；保留 45% 的融合
信号作为稳定项。这个比例是经验值，用 `rerank=False` 可以完全关闭重排并观察差异。

HTTP rerank 按通用 `/rerank` 协议实现，支持 `results[].index` 与
`relevance_score/score`。调用失败时，默认回退到启发式并记录 warning；设置
`RERANK_FALLBACK=false` 可以让失败直接暴露。

## 7. 生成与引用

### Mock 生成器

1. 用内容词计算问题与前三条命中的词面覆盖；
2. 覆盖率低于 28%，或匹配实词不足 2 个且问题不短，直接拒答；
3. 从每个命中中抽取最相关的句子：
   - 覆盖率、章节命中、数字/时效提示、句子长度共同打分；
   - 最多 3 条来自第一命中，后续各 2 条；
   - 全局去重，避免 FAQ 与正式政策重复句反复出现；
   - 「需要哪些材料」这类清单题，命中章节相关时按原文顺序取清单项；
4. 拼成「结论式引导 + 编号依据 + 参考来源」；
5. 引用编号只在真正使用的命中上生成。

这样做出的回答不是自然语言生成，但可审计、可复现，并且与 HTTP 生成器的接口一致。

### HTTP 生成器

- `/chat/completions`，`stream=true`；
- system prompt 约束「只依据资料、每句标号、资料不足只输出 NO_ANSWER」；
- 上下文按 `RAG_MAX_CONTEXT_CHARS` 截断，历史只保留最近 6 条、总额 1200 字；
- 参数：`temperature=0.2`、`max_tokens=800`，均可配置；
- 解析 SSE `data:` 行，忽略心跳；上游错误转成 `GenerationError`；
- 若模型漏标引用，追加来源清单，保证回答仍有可审计出处；
- 模型返回 NO_ANSWER 时丢弃引用，返回统一拒答模板。

### 为什么拒答要放在生成前

只靠提示词，模型仍可能在无关片段上「尽力回答」。词面证据门槛是硬闸：没有足够实词
覆盖就不进入生成。代价是某些语义改写会被误拒（例如完全用同义句提问），这时应通过
真实 embedding 或 query rewrite 改善，而不是放宽闸门到不可控。

## 8. 存储

### 表结构

- `documents`：source 唯一、content_hash、原文、mtime、size、metadata、时间戳；
- `chunks`：chunk_id 主键、doc_id 外键级联、source、heading_path JSON、ordinal、
  文本、embedding BLOB、embedding_dim；
- `corpus_meta`：schema_version、revision；
- 索引：source、doc_id、`(doc_id, ordinal)`。

### 向量格式

float32 小端 BLOB：

```python
array("f", vector).tobytes()
```

不走 JSON：JSON 浮点文本会让 512 维向量体积膨胀 3–5 倍，解析也慢。SQLite 没有原生
向量类型，BLOB 是单机阶段最直接的方案。显式处理大端字节序，避免跨平台读取出错。

### 并发

- 每操作独立 `sqlite3.connect`，不跨线程共享连接；
- `PRAGMA journal_mode=WAL`，读写互不阻塞；
- 写操作 `BEGIN IMMEDIATE`，失败回滚；
- `busy_timeout=5000ms`，避免短暂写锁立即报错；
- 外键开启，删除文档级联删除分块。

这解决的是单机多线程（FastAPI 线程池）场景，不是多进程/多节点写入。生产多实例需要
Postgres 或独立写服务。

### 增量

以文件内容 SHA-256 为幂等键，而不是 mtime。mtime 在复制、检出、容器重建后不可靠；
内容哈希能正确区分「没改」和「改了但 mtime 相同」。相同哈希直接跳过；不同哈希在
事务中删除旧文档再插入，保证分块不会残留。

## 9. 评测

### gold set

20 条样本，17 条可回答、3 条应拒答，覆盖四篇文档。每条包含：

```json
{"id":"q01","question":"...","expected_source":"01-售后与退货政策.md","key_points":["..."]}
```

### 指标

- **Recall@k**：期望来源是否出现在前 k 个检索结果中；
- **MRR**：第一个正确来源排名的倒数均值；
- **引用命中率**：最终回答的引用是否包含期望来源；
- **拒答准确率**：可回答未拒答 + 不可回答已拒答；
- **关键点覆盖率**：关键点内容词在回答中的覆盖率（阈值 50%）；
- **平均延迟**：检索 + 生成，本机进程内。

### 如何解读

当前结果（4 篇/49 分块）：

| 指标 | 值 |
| --- | ---: |
| Recall@1 | 70.6% |
| Recall@3 | 100% |
| MRR | 0.8529 |
| 引用命中率 | 88.2% |
| 拒答准确率 | 100% |
| 关键点覆盖率 | 98.0% |

这不是生产 benchmark。语料小、问题由作者编写、文档措辞与 gold 关键点高度相关，
分数偏高是预期内的。引用未命中的 2 条是 FAQ 与正式政策重复导致的多来源歧义；不打算
为了把数字拉满而删除 FAQ 或修改 gold set。真实上线应使用客服真实问题、历史工单和
多来源标注重新评测。

## 10. 成本与延迟预算

默认离线模式实测（本机、Python 3.14、49 分块）：

| 阶段 | 量级 | 说明 |
| --- | ---: | --- |
| 首次入库 4 篇 | ~90–100 ms | 解析、分块、哈希向量、写库 |
| 重复入库 | ~20 ms | 只做扫描与哈希比较 |
| 单次检索 | 几 ms | 49 分块线性余弦 + BM25 |
| mock 生成 | 10–20 ms | 抽取、排序、模板拼接 |
| 单题总计 | ~15–25 ms | 评测报告平均 18.6 ms |

真实模型模式下，延迟和成本主要取决于：

- embedding：批大小、模型维度、是否缓存查询；
- 生成：上下文长度（约 6000 字符上限）与 `max_tokens=800`；
- rerank：候选数量，默认只重排融合后的前 20 条。

按 512 维 float32 存储，每个分块向量约 2 KB；49 个分块不到 100 KB。即使 1 万个分块，
向量也只有约 20 MB，单机内存足够。真正的瓶颈是全量扫描和生成调用，而不是存储。

## 11. 安全与部署

- API Key 仅从环境变量读取，`Settings.describe()` 不输出密钥；
- SQLite 查询全部参数化，只有可控的字段名拼接（当前没有动态字段）；
- 日志使用结构化 JSON，异常按阶段归类，不返回第三方堆栈给最终用户；
- CORS 默认允许所有来源，仅适合内网；对外应改为白名单；
- `/api/ingest` 接受服务器路径，必须放在鉴权网关后并限制目录；
- 容器以非 root 用户运行，数据目录通过 volume 持久化；
- 健康检查只验证 DB 可读，不调用外部模型，避免模型故障导致容器反复重启。

## 12. 后续演进

按优先级：

1. 接入真实 embedding（bge-m3 / text-embedding-v3）并重建评测集；
2. 多来源 gold set，支持 `expected_sources` 列表，区分 FAQ 和政策原文；
3. Postgres + pgvector，向量检索下推，保留当前 RRF/重排层；
4. 增量删除同步与后台入库任务队列；
5. query rewrite 与多轮指代消解；
6. 文档级权限、审计日志和反馈闭环（有用/无用、纠错）。
